# 第 4 章 · 工具链与写作工作流

**本章目标：**

- 搭建一套顺手的 Markdown 编辑与预览环境
- 学会用 lint 规范文档格式
- 了解从写作到发布的完整工作流

## 4.1 编辑器方案

### VS Code（推荐，免费）

配合插件即可获得完整体验（安装方法见 [VS Code 教程](/tutorials/vscode/)）：

| 插件 | 作用 |
| --- | --- |
| **Markdown All in One** | 快捷键加粗/斜体、自动生成目录、列表自动续行 |
| **markdownlint** | 实时标记不规范写法（如标题跳级、行尾空格） |
| **Markdown Preview Enhanced** | 更强的预览（数学公式、导出 PDF） |

预览快捷键：`Ctrl+Shift+V`，侧边预览 `Ctrl+K V`。

### 其他方案

- **Typora**：所见即所得的沉浸式写作，付费（约 ¥89 买断），适合大量长文写作
- **Obsidian**：本地笔记 + 双向链接，适合个人知识库
- **在线方案**：语雀、Notion、掘金后台——打开即写，适合轻量场景

::: tip 选型建议
技术文档/项目 README 用 VS Code（跟代码同工作区）；个人知识管理用 Obsidian；偶尔写一篇用在线平台。
:::

## 4.2 markdownlint：让文档格式统一

markdownlint 插件按规则集检查文档，常见规则：

| 规则 | 含义 |
| --- | --- |
| MD001 | 标题不跳级 |
| MD013 | 行长限制（默认 80 字符，中文语境常关闭） |
| MD007 | 无序列表统一缩进（2 空格） |
| MD032 | 列表前后需空行 |
| MD041 | 文件第一个块必须是标题 |

::: info 团队协作视角
代码有 ESLint，文档就该有 markdownlint——多人共写文档时统一规则，能消灭"每个人格式都不一样"的问题。可在 `.markdownlint.json` 中按团队习惯定制。
:::

## 4.3 图片管理

图片是文档维护中最容易失控的部分，两条实用策略：

**1. 项目内相对路径**（推荐用于代码仓库）

```text
my-project/
├── docs/
│   ├── images/        # 图片统一放这里
│   │   └── architecture.png
│   └── readme.md      # 引用：![架构](./images/architecture.png)
```

优点：图片与文档同仓库版本管理，永不失效。

**2. 图床**（适合博客等独立发布场景）

把图片上传到对象存储或图床服务（如 GitHub 仓库 + jsDelivr、阿里云 OSS），文档里引用 URL。优点是任何地方都能访问，缺点是依赖外部服务的稳定性。

::: warning 图床风险
免费图床随时可能关停导致全部图片失效。重要文档优先选择"仓库内相对路径"。
:::

## 4.4 从写作到发布的完整工作流

以"给开源项目写文档"为例，典型工作流：

```text
1. VS Code 中用 Markdown 写作（markdownlint 保证格式）
2. 本地预览确认渲染效果
3. git 提交（docs: 前缀，见 Git 教程第 7 章）
4. push 到 GitHub —— README/issue 自动渲染
5. 文档站由构建工具（如 VitePress）自动部署
```

本站（CS101）就是这么运作的：**每一篇教程都是 Markdown 源文件**，经 VitePress 构建成你正在阅读的网站。

## 4.5 高效写作的几个习惯

- **先写大纲再填肉**：先用标题搭好骨架，再逐节填充，避免写着写着跑偏
- **一段一个意思**：段落短，信息密度高，扫读友好
- **多用表格与列表**：并列信息用列表，对比信息用表格，别写成"大段落"
- **代码块必带语言标识**：高亮与否，专业度立现（见第 2 章）
- **发布前通读一遍**：检查链接有效性、错别字、渲染效果
