**本章目标：**

- 说清内核态与用户态这条边界，以及一次系统调用究竟怎么跨过它
- 能用「虚拟化」与「并发」两条主线解释进程、虚拟内存、文件描述符这几个抽象从哪来
- 完整追踪一次 `read`：从 C 库包装函数一路走到磁盘，再回到用户缓冲区

## 1.1 先把操作系统拿掉

早期计算机没有操作系统：程序直接面对硬件，运行时独占整机。这种模式有三个绕不开的问题。

```text
独占      你的程序跑 3 小时，下一个人就等 3 小时；而它大部分时间在等键盘输入
无保护    一条指令就能改中断向量表、改写别人的内存，程序之间互相踩死
重复劳动  每个程序都要自带磁盘驱动、网卡驱动、终端控制代码
```

操作系统的答案是**加一个常驻中间层**：先把杂乱硬件包装成统一抽象，再把抽象分时借给多个程序，并在借用者之间做仲裁与计量。

```text
没有 OS    程序 ────────────────────── 硬件（真实资源：独占、无序、无保护）
有 OS      程序 ── 抽象 ── 内核 ── 驱动 ── 硬件
                  进程 / 虚拟地址空间 / 文件描述符：受控、可复用、可计量
```

:::tip[一句话定义]
操作系统 = 资源管理器 + 抽象层。前者决定「谁能用、用多久、用多少」，后者决定「硬件以什么接口出现」。本教程后面所有机制都是这两句话的展开。
:::

理解了这个中间层，很多现象就顺理成章：为什么 `kill -9` 只能由同一用户或 root 发出（仲裁权在内核手里），为什么普通用户改不了别人的文件权限（抽象的元数据由内核保管），为什么写 C 程序不需要懂硬盘寻址（驱动把那层细节吃掉了）。

## 1.2 内核态与用户态：一条硬件强制的红线

x86 定义了 4 个特权级（ring 0 到 ring 3），现代通用操作系统实际只用两个：

```text
ring 0  内核态：可执行特权指令 —— 改页表基址 CR3、开关中断、直接访问 IO 端口
ring 3  用户态：上述指令一律触发异常；访问未映射地址由内核判为段错误
```

这条线不是软件约定，而是 CPU 硬件在每次取指时检查的标志位。用户态程序遇到**中断、异常、陷入**三类事件才会进入内核，处理完再退回。

```bash
# 每个进程的状态里就能看到它当前跑在哪一层
ps -o pid,stat,user,comm -p 1
cat /proc/1/status | grep -i -E 'Uid|Gid|State|CapEff'
```

`/proc/1/status` 里的 `CapEff` 是进程的 capability 位图，`root` 也不等于无所不能：容器里 root 干不了的事，多半就是这里的位被内核裁掉了（见 [第 9 章 · 虚拟化与容器的内核基础](../09-virtualization-container/)）。

## 1.3 系统调用是怎么发生的

用户程序唯一合法的跨线方式是**陷入（trap）**。x86-64 Linux 的调用约定非常直白：

```text
1. 系统调用号放进 rax（read 是 0，write 是 1）
2. 参数依次放 rdi、rsi、rdx、r10、r8、r9（最多 6 个）
3. 执行 syscall 指令 —— CPU 切到内核态，跳到 MSR 登记的入口地址
4. 内核先校验参数：指针是否落在用户地址范围、fd 是否有效、长度是否为负
5. 干活，然后 sysret 回用户态，返回值放 rax
```

```c
/* 用户态写的这一行，实际上是「glibc 包装函数 + syscall 指令」 */
#include <unistd.h>
#include <errno.h>

ssize_t n = read(fd, buf, sizeof buf);   /* 内部：rax = 0，然后 syscall */
if (n == -1) {
    /* errno 由 glibc 从内核返回的负值翻译而来，不是内核直接写的 */
    perror("read");
}
```

在汇编层看同一个调用，界限感会更清楚（下面只是示意，不建议手写）：

```text
mov rax, 0          ; sys_read 调用号
mov rdi, 1          ; fd
mov rsi, buf        ; 目的缓冲区
mov rdx, 1024       ; 请求字节数
syscall             ; ← 这一条指令就是「跨线动作」，之后 CPU 已在 ring 0
```

:::caution[别写死系统调用号]
调用号跟架构走，x86-64 与 aarch64 的同名调用编号不同。Linux 承诺稳定的是 **syscall ABI**（语义与结构体布局），不是「编号全网通用」。业务代码请用 libc 包装函数；确实需要裸调用时以 `man 2 syscall` 与 `<asm/unistd.h>` 实测为准。
:::

**错误写法 → 正确写法**：这是本章最想让你带走的一个习惯。

```c
/* 错误写法：假定 read 一定给满 1024 字节 */
read(fd, buf, 1024);            /* 返回值被丢弃 */
process(buf, 1024);             /* 可能读到半个包，或者 EOF 时读到垃圾 */

/* 正确写法：先看返回值，再决定处理多少字节 */
ssize_t n = read(fd, buf, sizeof buf);
if (n < 0) {
    if (errno == EINTR) { /* 被信号打断：这不是失败，应当重试同一次读 */ }
    perror("read");
    return 1;
}
if (n == 0) { /* 到达 EOF，不是错误 */ }
process(buf, (size_t)n);              /* 只处理真正读到的部分 */
```

原因：`read` 的语义是「**最多**读这么多字节，返回实际读到的数量」。管道、终端、socket、以及一个尚未写完的普通文件都可能返回短计数。把「短读」当「错误」，或者把返回值当固定值，是并发与 IO bug 的头号来源（[第 6 章 · 输入输出与中断](../06-io-interrupt/) 里讨论 `select`/`epoll` 时会再用到这条）。

## 1.4 两个核心抽象预告：进程与文件描述符

后面所有章节都会反复使用这两个词，先把它们的感觉建立起来。

**进程**是「 CPU 借用凭证 + 独占资源账本」。程序是磁盘上的静态字节，进程是内核为它建立的一套运行实例：一段虚拟地址空间、一个执行流、一组已打开文件、一份身份（uid/gid）与配额。同一份 `nginx` 二进制可以有 8 个进程实例，各自独立。

**文件描述符**是「一切皆文件」的把手。它是每个进程私有的小整数（0、1、2 起步），指向内核里的一张表项，而表项背后可以是普通文件、目录、socket、管道、终端、定时器甚至事件队列。

```bash
# 一个真实进程持有的一切，都能通过 fd 编号看到
ls -l /proc/self/fd
cat /proc/self/fd/1        # fd 1 指向哪里？通常是终端设备

# 系统允许单个进程开多少个 fd
ulimit -n
cat /proc/sys/fs/file-max  # 整机上限，以内核配置为准
```

进程与 fd 为什么值得单独抽象？因为它们把「身份」和「能力」解耦了：进程决定你是谁、能看哪段内存；fd 决定你能对哪个对象下什么指令。安全性正来自这种分离 —— 拿到一个只写 fd 的程序，无论如何也读不到那个文件。

## 1.5 两条主线：虚拟化与并发

操作系统的全部机制可以拆成两句话：**把一份资源虚拟成多份**（虚拟化），以及**让多个执行流在没有明显干扰的情况下共存**（并发）。

```text
虚拟化                        并发
CPU  → 进程/线程              多个执行流争用同一资源 → 需要调度与仲裁
内存 → 虚拟地址空间            两个进程都以为独占内存 → 需要隔离与保护
磁盘 → 文件/文件系统          多个写者同时改同一文件 → 需要锁与一致性
网络 → socket                 多个连接共享带宽 → 需要排队与限流
```

两条主线交织出的问题清单，就是本教程的目录：

- 虚拟化什么时候会「露馅」？—— 缺页、换页、OOM（[第 4 章 · 内存管理与虚拟内存](../04-memory/)）、缓存未命中（[第 5 章 · 文件系统](../05-filesystem/)）、中断与 DMA（[第 6 章 · 输入输出与中断](../06-io-interrupt/)）
- 并发带来的不只是性能，还有正确性问题 —— 竞态与锁（[第 7 章 · 并发与锁](../07-concurrency-locks/)）、死锁（[第 8 章 · 死锁与同步原语](../08-deadlock-sync/)）
- 仲裁本身要花钱 —— 上下文切换（[第 2 章 · 进程与线程](../02-process-thread/)）、调度延迟（[第 3 章 · CPU 调度](../03-cpu-scheduling/)）、系统调用开销（本章 1.6）

:::tip[判断自己是否「懂原理」的方法]
遇到任何慢或怪的现场，能把它归到这两条主线之一：是虚拟化在补账（换了页、丢了缓存），还是并发在排队（等锁、等调度）？答得出来，接下来的排查方向就唯一了。
:::

## 1.6 看一次 read 走过的路

下面是一次冷读的完整路径（热读在第 5 章的页缓存里就结束了）。函数名随内核版本会变，看层次即可，别背符号；想核对可在装了内核调试符号的机器上用 `sudo cat /proc/kallsyms | grep -i x64_sys_read` 实测。

```text
用户态
  your code → glibc read(fd, buf, n)        把 0 放进 rax，执行 syscall
──────────────────────── 陷入：ring 3 → ring 0 ────────────────────────
内核态
  系统调用入口                               保存寄存器，切到内核栈
  fd 校验                                    查当前进程的 fd 表 → 拿到 file 对象
  VFS 层 read_iter                           按 file 对象的 f_op 分派给具体实现
  ext4 层                                     逻辑块号映射到分区内的物理块
  页缓存未命中 → 分配页 → 提交 BIO
  块层 / blk-mq                               合并、排队、调度
  NVMe 驱动                                   写提交队列，敲门铃（doorbell）
  中断处理（硬中断 → 软中断）                   DMA 已把数据写进内存，内核唤醒等待队列
  copy_to_user(buf, page, n)                  把内核页里的数据拷到用户缓冲区
──────────────────────── 返回：ring 0 → ring 3 ────────────────────────
用户态
  rax = 实际读到的字节数；n < 0 时 errno 已就绪
```

三个必须记住的结论：

```text
1. 系统调用有固定成本（保存/恢复上下文、参数校验、缓存被扰动），不是函数调用那么便宜
2. read 的返回值与「磁盘访问次数」无关：可能一次磁盘都没碰（命中缓存），也可能读 1 字节也搬 4KB
3. 数据是 DMA 直接写进内存的，CPU 只负责下达指令与善后 —— 「拷数据」和「等数据」是两回事
```

## 1.7 综合练习：给一次 read 计时，判断它去没去磁盘

写一个最小程序，读同一个大文件两次，第一次是冷的、第二次是热的：

```c
/* warm.c —— 编译：cc -O2 warm.c -o warm */
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

static double now_ms(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);      /* 别用 gettimeofday：它会被校时影响 */
    return ts.tv_sec * 1000.0 + ts.tv_nsec / 1e6;
}

int main(int argc, char **argv) {
    if (argc < 2) { fprintf(stderr, "usage: %s <file>\n", argv[0]); return 2; }
    size_t cap = 1u << 20;
    char *buf = malloc(cap);
    for (int round = 0; round < 2; round++) {
        int fd = open(argv[1], O_RDONLY);     /* 普通缓冲 IO，走页缓存 */
        if (fd < 0) { perror("open"); return 1; }
        double t0 = now_ms();
        ssize_t total = 0, r;
        while ((r = read(fd, buf, cap)) > 0) total += r;
        double dt = now_ms() - t0;
        printf("round %d: %zd bytes in %.1f ms (%.1f MB/s)\n",
               round, total, dt, total / dt / 1000.0);
        close(fd);
    }
    return 0;
}
```

```bash
dd if=/dev/zero of=/tmp/big.bin bs=1M count=512 status=none
sync
echo 3 | sudo tee /proc/sys/vm/drop_caches   # 丢掉页缓存，制造冷读
./warm /tmp/big.bin
./warm /tmp/big.bin                          # 第二次：缓存已热
```

观察并回答三问：两轮的 MB/s 差多少倍？第二轮为什么几乎不需要磁盘时间（对应 1.6 的哪一步）？如果再用 `strace -T -e trace=openat,read,close ./warm /tmp/big.bin` 看单次 `read` 耗时，`O_DIRECT` 与 `fdatasync` 的差别会出现在哪里？

:::caution[`drop_caches` 只该用来做实验]
它会让机器上所有进程的缓存瞬间变冷，线上执行等于一次人为故障演练。写进脚本前先确认自己在测试机上。
:::

## 本章小结

- 操作系统是常驻中间层：把硬件包装成受控抽象，再把抽象分时借给多个程序并做仲裁
- 用户态与内核态的边界由 CPU 特权级硬件强制；唯一合法通道是陷入，即 `syscall` 指令 + 调用号与参数寄存器约定
- 进程与文件描述符分别承载「身份/资源账本」与「能力把手」，两者的分离是安全模型的基础
- 虚拟化与并发是贯穿全部机制的两条主线：慢与怪的问题都能归到「补虚拟化的账」或「在并发里排队」
