**本章目标：**

- 用"接口变不变、谁决定加行为"两个维度区分适配器、装饰器、代理、外观
- 能为接口不匹配的三方代码选出代价最低的适配做法
- 识别外观与动态代理被滥用的信号，避免把系统包成黑箱

## 3.1 结构型看的是「谁连着谁」

创建型管对象怎么出生，结构型管对象**怎么连接**：类与类、模块与模块之间的连线形状决定了改一处会不会牵全身。本章四个模式都围绕同一个动词——**包一层**，区别全在"包这层是为了什么"：

| 模式 | 接口变不变 | 包这层的动机 |
| --- | --- | --- |
| 适配器 | 变（转成目标接口） | 两边接口对不上 |
| 装饰器 | 不变 | 客户端自愿叠加行为 |
| 代理 | 不变 | 控制访问，客户端常不知情 |
| 外观 | 重新设计（更简单） | 替整个子系统提供一个入口 |

共同代价：多一层间接、多一次调用、多一个要维护的类型。逐个看。

## 3.2 适配器：接口不匹配的三种做法

**不用它**：旧代码统一依赖 `fetch()` 返回字符串；新采购的 SDK 只有 `get_data()` 返回字节。要么改一百处旧调用（侵入大、回归风险高），要么在调用点手写转换（重复且散落）。
**用了之后**：转换收进一个类，旧代码一行不动，SDK 换货时也只改适配器。
**代价**：一层转发；语义有损（超时、错误约定可能被抹平）；双向、一对多的适配网会变成泥潭。

接口不匹配有三种做法，代价从低到高：

```python
# 做法一：转换函数/闭包——一次性桥接，不引入新类型
fetch = lambda: sdk.get_data().decode("utf-8")

# 做法二：对象适配器——组合被适配者，实现目标接口（最常用）
class SdkAdapter:
    def __init__(self, sdk):
        self._sdk = sdk

    def fetch(self):                    # 旧代码要的接口
        return self._sdk.get_data().decode("utf-8")

# 做法三：类适配器——同时继承两边，在 Python 里就是多继承拼
class LegacyAdapter(BaseFetcher, NewSdk):
    def fetch(self):
        return self.get_data().decode("utf-8")
```

选择口径：一次性桥接用函数；要进类型体系、要被注入复用用对象适配器；类适配器把两边实现焊死在同一对象上，两边任何一方法名冲突都会引发排雷——能用组合就别用继承（[第 1 章 · 面向对象原则与模式的语言](../01-principles/) 的结论在这里直接兑现）。

:::caution[适配器不是翻译层堆积场]
每个适配器都是一份"两边接口的活文档"，SDK 升级时全部要复查。出现"适配器的适配器"时，说明该正经抽一层内部接口，而不是继续套娃。
:::

## 3.3 装饰器：可插拔的包装

**不用它**：给文件流加压缩、加密、缓冲、日志四种行为，用继承表达就是 2 的 4 次方个子类；或者把这四种行为全塞进原类，原类胖成球还改不动。
**用了之后**：每种行为一个小包装类，与原件同接口，按需叠罗汉。
**代价**：层数一多调试栈难读；包装后对象身份变了；忘了保留元信息则文档与类型跟着失真。

```python
class CompressionStream:            # 与被包装对象同接口，调用方无感
    def __init__(self, inner):
        self._inner = inner

    def write(self, data):
        self._inner.write(zip.compress(data))

    def read(self):
        return zip.decompress(self._inner.read())

stream = Buffering(Compression(FileStream(path)))   # 像套娃，也像点菜
```

装饰器与继承的对照是关键考点：

| 维度 | 继承扩展 | 装饰器扩展 |
| --- | --- | --- |
| 绑定时机 | 编译期写死 | 运行时随意组合 |
| 行为数量 | 指数级子类 | 线性级包装类 |
| 原类是否改动 | 要（或派生） | 完全不动 |

:::tip[别和 Python 的 @decorator 混为一谈]
`@lru_cache` 这类函数装饰器是"接收函数返回函数"的语法糖，思想一致（不改原件、透明加行为），但 GoF 装饰器是**类与对象**层面的模式，通常要求包装后保持同一接口。面试与读码时这两个语境经常撞车，先分清。
:::

错误写法 → 正确写法示范代价：

```python
# 错误：装饰完再比较身份/注册回调，打的是包装体，
# 拆包时原件根本找不回来
x = Logging(x)
assert x is original          # 失败——每包一层，身份就断一次

# 正确：要么把包装类设计成可解包（保留 inner 引用），
# 要么在装饰前完成对原件的注册
```

## 3.4 代理：同接口背后换个主人

**不用它**：查询直接打数据库，热点数据反复查库；远端调用的重试、超时逻辑抄了七遍散在业务里。
**用了之后**：客户端拿到的仍是"那个对象"（同接口），但访问被中间人管控——可以缓存、懒加载、鉴权、记账。
**代价**：多一跳延迟；缓存一致性要自己管；代理通常不由客户端创建，依赖变得更隐形。

```python
class CachedUserRepo:             # 透明代理：接口与真实主体完全一致
    def __init__(self, inner):
        self._inner = inner
        self._cache = {}

    def get(self, uid):
        if uid not in self._cache:
            self._cache[uid] = self._inner.get(uid)
        return self._cache[uid]
```

按动机分四类：**缓存代理**（省重复开销）、**虚拟代理**（昂贵对象先占位后创建，如按需加载大图）、**保护代理**（按权限放行方法调用）、**远程代理**（本地替身把调用变成网络请求）。

与两个近亲划界——三者都能"包一层"，看接口与动机：

```text
适配器：接口变了（把 A 转成 B）
装饰器：接口不变，客户端主动加行为（包裹是可见决定）
代理：  接口不变，控制访问（存在与否常由工厂/框架决定）
```

:::caution[缓存代理的失效是设计题]
示例里"只进不出"的缓存会让更新后的数据永远读旧值。上线前必须回答：谁负责失效（写路径联动？TTL？版本号？），缓存的粒度与上限多大。代理只帮你把这件事集中做，不替你决定策略。
:::

## 3.5 动态代理：框架里的隐形手

上面的代理要手写目标类的每个方法。当接口有几十个方法、且每个方法都要"拦截"时，框架改用**运行时生成的代理**：不写实现，把任意方法调用统一送进一个处理器。

```python
# 迷你动态代理：__getattr__ 兜住"没写过的方法"（伪码，
# http_post 表示一次序列化 + 网络调用）
class RpcStub:
    def __init__(self, endpoint):
        self._ep = endpoint

    def __getattr__(self, name):
        def call(*args):
            return http_post(self._ep, {"method": name, "args": list(args)})
        return call

users = RpcStub("http://svc/rpc")
users.get(42)          # 没人写过 get 方法——被拦截并变成了网络调用
```

Java 生态里这是基础设施级别的技术：JDK 动态代理沿接口生成代理类，CGLIB 则通过生成子类工作；Spring 的声明式事务、MyBatis 的 Mapper 接口、各 RPC 框架的客户端桩，背后都是同一机制——你只声明接口，框架在运行时替你实现"所有方法"。

```java
// JDK 动态代理：接口不用写实现，所有方法调用都汇入一个 handler
Object stub = Proxy.newProxyInstance(
    loader, new Class[]{UserRepo.class}, handler);
// handler.invoke(obj, method, args) 里统一做序列化/重试/事务
```

**不用它**：给 30 个方法手写 30 个转发，每个转发里再抄一遍重试/日志/序列化样板。
**用了之后**：横切逻辑收进一个拦截器，接口即能力清单。
**代价**：生成的代码看不见摸不着，断点难下；有调用开销；类型安全下降——方法名拼错不会编译期报错，而是变成一个"合法"的远程调用。

:::danger[动态代理吞掉拼写错误]
`__getattr__` 式代理里，`user.nmae` 不会报 AttributeError，而可能返回一个新闭包或发出一次远端查询。生产级框架的拦截器都要校验"这个名字是否在合法方法表内"，不在就立刻抛错——自己写动态代理时这条绝不能省。
:::

## 3.6 外观：划定子系统边界

**不用它**：下单流程要亲手编排库存校验、计价、开票、推送四个服务，每个新调用方都重抄一遍同样的顺序，参数传错顺序的事故时有发生。
**用了之后**：一个门面类按**用户任务**提供入口，子系统内部演进不再冲击调用方。
**代价**：多一个类；有时客户端确实需要绕过门面直连子系统，边界要留活口。

```python
# 错误：调用方编排子系统——顺序知识散写七处
stock.check(cart)
price.calc(cart)
invoice.create(cart)
notify.push(cart)

# 正确：外观以"用户想完成的事"命名，不以"子系统有什么方法"命名
class OrderFacade:
    def __init__(self, stock, price, invoice, notify):
        self._deps = (stock, price, invoice, notify)

    def place_order(self, cart):        # 编排知识收到一处
        s, p, i, n = self._deps
        s.check(cart); p.calc(cart); i.create(cart); n.push(cart)
        return order_id(cart)
```

注意方法命名的信号意义：`place_order` 是任务，`stock_check` 是转发——外观的价值在于**划定子系统边界**，把"什么可以离开这个模块被讨论"钉在这里，而不是给零件们当传声筒。

:::caution[外观滥用的三个信号]
1. 门面长到五六十个方法，成了新的上帝类——它已不再"简化"，只是"收容"；
2. 门面里开始出现业务分支（if 会员 then 走另一流程）——编排之外的知识混进来了；
3. 每个模块都被强行包一层外观，即使没有任何跨模块调用方——纯仪式。正确做法是按用例拆薄门面（`AuthFacade`、`ProfileFacade`），而不是养一个厚门面。
:::

## 3.7 综合练习：四兄弟识别

四个场景各对应本章哪个模式？写出名字与判定的那句话理由。

1. 遗留的 CSV 报表模块只认"老接口"，而新采集器是另一套方法名，需要让旧模块不改代码继续工作。
2. 给已有的支付服务依次加上日志、限流、审计三种行为，原类不许改动，三种开关按环境自由组合。
3. 用户对象访问数据库，但读请求九成是重复热点，要求"用户无感"地先走缓存。
4. 报表功能内部分为取数、聚合、排版、导出四个模块，团队要求其他模块只准调用一个入口类。

答案要点：1 → 适配器（两边接口对不上，接口被转换）；2 → 装饰器（同接口、客户端自愿叠加、可自由组合）；3 → 代理（同接口、访问控制、客户端不知情）；4 → 外观（一个入口代表整个子系统）。再加一问自查：场景 2 若改为"每种开关组合生成一个子类"，会膨胀成几个类？（三种开关全组合 = 8 个，这就是 3.3 表格里"指数级"的含义。）

## 本章小结

- 四个模式都是"包一层"，靠两问定性：接口变没变（变 → 适配器），这层为谁存在（客户端自愿 → 装饰器；管控访问 → 代理；代表子系统 → 外观）
- 装饰器以线性包装类替代指数级子类，代价是对象身份断裂与调试栈变深；动态代理把手写转发升级成运行时生成，代价是隐形代码与拼写错误不被拦截
- 缓存代理只集中了失效问题、并不替你回答失效策略；外观以用户任务命名才有边界价值，出现转发方法或业务分支就是滥用信号
- 下一章三个结构型模式（桥接、组合、享元）处理另外三种连线病：双维度继承爆炸、叶与容器不统一、海量细碎对象
