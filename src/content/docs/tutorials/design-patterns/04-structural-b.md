**本章目标：**

- 能用桥接拆开"抽象 × 实现"的继承爆炸，并指出它与适配器的时机差异
- 解释组合的统一接口代价、享元的内蕴/外蕴状态切分与池化陷阱
- 判断依赖注入该手工装配还是交给容器，并完成结构型模式选型自查

## 4.1 桥接：把「抽象 × 实现」从继承里解救出来

**不用它**：报表要支持"普通/汇总/明细"三种抽象 × "MySQL/Postgres"两种数据后端，用继承表达就是 3 × 2 = 6 个类；再加一种后端，六个抽象全要多写一层。
**用了之后**：抽象侧持有实现侧的引用，两个维度各自独立扩展——3 个抽象类 + 2 个实现类。
**代价**：设计期就要预见两个正交维度；只有一个维度时，这层拆分是纯开销。

```python
# 错误写法：维度乘积——每加一个后端就重写一整排抽象
class MysqlNormalReport(MysqlReport): ...
class PgNormalReport(PgReport): ...          # 6 个类，改 1 处动两维

# 正确写法：抽象与实现各走各的继承树，靠引用连接
class Report:                                # 精化抽象：报告"是什么"
    def __init__(self, backend):
        self._backend = backend              # 组合，不是继承

    def export(self, sql):
        return self.render(self._backend.query(sql))  # "数据从哪来"交给实现侧

class MysqlBackend:
    def query(self, sql): ...

class PgBackend:
    def query(self, sql): ...

# NormalReport / SummaryReport 等继承 Report，只写渲染差异
report = Report(PgBackend())                 # 两维度任意配对，无需新类
```

桥接与适配器长得像（都涉及两个类的连接），区别在**时机与方向**：适配器是事后救火——两个既有接口对不上，套一层转换；桥接是事前设计——预见到抽象和实现会各自演化，一开始就不让它们继承纠缠。

:::tip[识别桥接的信号]
当你发现自己在给继承树"补另一棵树的分支"（每种抽象都要 × 每种平台），就是乘法要变成加法的时刻：把变化的那一维抽成被组合的接口。消息系统的"紧急程度 × 发送渠道"、设备驱动的"遥控器 × 品牌"都是同一形状。
:::

## 4.2 组合：叶与容器说同一种语言

**不用它**：文件系统/菜单/组织架构这类树形结构，调用方永远在写"它是叶子还是容器"的分支，遍历逻辑散落各处且层层复制。
**用了之后**：Leaf 与 Composite 实现同一个组件接口，客户端对整棵树只有一句 `node.size()`——递归下沉到结构内部。
**代价**：接口被"拉平"到叶与容器的最小公约数，容器专属操作（add/remove）被迫出现在叶子身上（LSP 阴影）；类型检查能力丧失。

错误写法 → 正确写法对照：

```python
# 错误：客户端被迫了解树的结构
def total_size(node):
    if isinstance(node, File):
        return node.size
    acc = 0
    for child in node.children:              # 文件夹才有的分支
        acc += total_size(child)
    return acc

# 正确：统一组件接口，叶与容器同语言
class File:
    def size(self):
        return self._nbytes

class Folder:
    def size(self):
        return sum(child.size() for child in self._children)

total = root.size()            # 客户端对树一无所知，也不需要知道
```

:::caution[组合与 ISP 的张力]
为了让客户端"一视同仁"，组件接口必须取两类节点的并集：`add_child` 挂在叶子上只能抛异常或空实现——这正在违反接口隔离与里氏替换。取舍口径：操作以"聚合/遍历"为主 → 用组合求统一；操作频繁区分节点类型 → 放弃统一接口，让容器与叶子各自显式建模（类型系统会帮你挡错）。
:::

判断自己是否**不**需要组合的土办法：数一数客户端代码里 `isinstance` 分支——如果每种操作都必须先问"这是什么节点"，统一接口并没有带来收益，只剩泛化接口的害处。

## 4.3 享元：内蕴与外蕴状态的切分

**不用它**：文本渲染器给每个字符建一个对象，一百万个字符就是上百万份字形数据（曲线轮廓、字宽），内存与构建开销爆炸。
**用了之后**：相同字符共享同一个字形对象（**内蕴状态**，不随位置变化、可共享），出现位置、字号、颜色（**外蕴状态**，每次不同）由调用方传入。对象数从"字符总数"降到"字符种类数"。

```python
class Glyph:                       # 内蕴状态：字形轮廓，每字符仅一份
    def __init__(self, outline):
        self.outline = outline

_GLYPHS = {}
def glyph_for(ch):                 # 池：同字符永远同一个实例
    if ch not in _GLYPHS:
        _GLYPHS[ch] = Glyph(load_outline(ch))
    return _GLYPHS[ch]

class RenderedChar:                # 外蕴状态：每次出现各自一份
    def __init__(self, ch, x, y, size):
        self.glyph = glyph_for(ch)
        self.x, self.y, self.size = x, y, size

    def draw(self, ctx):
        ctx.paint(self.glyph.outline, self.x, self.y, self.size)
```

池化注意两点：一是并发创建（多线程可能各造一份再覆盖，需要锁或语言原生的缓存语义）；二是池的生命周期（享元的粒度从"程序运行期常驻"到"带淘汰的缓存"不等，后者已是缓存策略题而非纯模式）。

Python 里享元有语言内置的现象：CPython 缓存小整数对象、intern 部分字符串，所以两个变量"值相等且 is 也相等"有时成立。

:::caution[别把语言巧合当合同]
上述内建缓存是 CPython 实现细节，语言规范并不保证，跨实现与跨版本都会变。业务要共享就自己建池（如上面的 `glyph_for`），让共享行为写在代码里而不是指望运行时。
:::

**代价**：状态切分是易错的重构——把本该外蕴的状态（如坐标）塞进共享对象，所有实例一起错；切分不彻底则共享率名存实亡。此外内蕴状态必须不可变，否则共享等于互相污染。现代托管运行时里，除非确属海量细碎对象，GC 分配器的快路径常常已经够了——享元要测量后再上，不是直觉先行。

## 4.4 依赖注入：它不算 GoF 模式，而是 DIP 的施工法

先回答"依赖注入是不是模式"：GoF 23 个里没有它——它是第 1 章 DIP 的工程惯例，这个词约在 2004 年前后被总结出名，此后常与服务定位器对照讨论，本节末尾会厘清两者边界。本节仍按三段式评估。

**不用它**：类在内部自行 new 依赖——依赖清单看不见（藏在方法体里），测试与生产被迫共用同一套真实连接。
**用了之后**：依赖从外部（构造函数/参数）注入，类只声明"需要什么角色"，真假实现随意换。
**代价**：装配知识集中到入口，对象图一大，手工接线本身就成为需要管理的东西（引出 4.5）。

```python
# 错误：隐藏依赖——测试被一个连接字符串绑架
class OrderService:
    def __init__(self):
        self.repo = OrderRepo("mysql://127.0.0.1/app")

# 正确：依赖由外界注入，类自己不挑实现
class OrderService:
    def __init__(self, repo, notifier):
        self.repo, self.notifier = repo, notifier
```

```java
// Java 语境里"注入"常以注解出现，本质相同：
// 声明需求，由框架在运行期把实例塞进构造器或字段
@Service
class OrderService {
    private final OrderRepo repo;
    OrderService(OrderRepo repo) { this.repo = repo; }
}
```

三种形式（构造器/设置方法/接口注入）中优先**构造器注入**：依赖一次配齐、对象出生即合法。警惕**服务定位器**变体——类里写 `container.get(OrderRepo.class)` 看似解耦，实是把依赖查找搬回类内部，重新制造了隐形依赖，只配在框架边界使用。

## 4.5 容器与手工装配：谁接线，接多少

依赖注入的"装配"这一步有两种做法。手工装配（composition root）：在一个入口文件里按拓扑顺序逐个 new——

```python
# main.py —— 手工接线：代码即依赖图，可 grep、可单步
def build_app(settings):
    repo = OrderRepo(settings.db_url)
    notifier = MailNotifier(settings.smtp)
    service = OrderService(repo, notifier)
    return App(service)
```

DI 容器：登记"接口 → 实现"与生命周期（单例/请求级/瞬态），由容器解析整张依赖图、自动补齐参数。

| 维度 | 手工装配 | DI 容器 |
| --- | --- | --- |
| 可见性 | 入口文件就是依赖图 | 图藏在注解/注册表里 |
| 重构友好度 | 直接改代码，编译器/静态检查护航 | 隐式解析，改签名易漏 |
| 生命周期管理 | 自己写，行数不多 | 内置多种作用域 |
| 出错形态 | 启动即 Python 栈回溯，直白 | "未注册/循环依赖"框架报错 |
| 适用规模 | 中小项目、入口 1—2 个 | 模块数十以上、作用域复杂 |

:::danger[循环依赖是设计警报，不是配置题]
容器报错"A 依赖 B、B 依赖 A"时，用容器提供的延迟注入/作用域技巧"绕过去"往往是在掩盖职责划分错误。正确反应回到第 1 章：拆类、抽接口、或让共享依赖下沉为第三个模块。
:::

Python 社区的整体经验：中型以下项目，手工装配 + 工厂函数通常已经足够，还天然满足测试需求（入口传假货即可）；容器真正的增值点是**多作用域生命周期**（如每请求一个事务上下文）与跨包自动扫描，没有这两个需求就别引入魔法。

## 本章小结

- 桥接把"抽象 × 实现"的继承乘积拆成两棵独立树靠引用连接，是事前设计；适配器是两个既有接口的事后救火
- 组合用统一组件接口换来"对整棵树说一句话"，代价是接口泛化与类型检查丧失——客户端频繁区分节点类型时别硬统一
- 享元 = 不可变的内蕴状态进池 + 可变的外蕴状态由调用方传入；先测量再上，语言内建缓存（小整数、intern）不可当合同依赖
- 依赖注入是 DIP 的施工法而非 GoF 模式：构造器注入优先，服务定位器重造隐形依赖；中小项目手工装配通常是 Python 的正解
