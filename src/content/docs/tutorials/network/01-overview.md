**本章目标：**

- 说清网络为什么必须分层，层与协议各自解决什么问题
- 对齐 OSI 七层与 TCP/IP 四层，能判断一个工具工作在哪一层
- 跟踪一次 HTTP 请求从应用层到网卡的封装与解封装全过程

## 1.1 为什么分层

如果通信是「一根线两端说话」，根本不需要分层。真实需求是：同一条消息要穿过网线、光纤或 WiFi，经过几台到十几台路由器，跨越不同厂商的设备，还要保证不丢、不重、不乱序。把这些塞进一个巨型协议里，任何一方改动都会牵一发动全身。

分层是软件工程最朴素的答案：**每层只对上一层提供一种能力，只对下一层提要求**。

```text
不分层：  应用 ───────────────────────────── 对端应用   （改哪都崩）

分层：    应用 │ 传输 │ 网络 │ 链路 │ 物理
            ↓     ↓     ↓     ↓     ↓
          报文   段    分组   帧    比特
          只管业务 只管端到端 只管跨网 只管这一跳 只管电信号
```

分层换来三件实实在在的好处：

```text
1. 可替换：WiFi 换成网线，上层完全不知道（链路层变了，IP 分组还是那个 IP 分组）
2. 可分工：网卡厂商只实现链路层，操作系统实现网络层+传输层，你只写应用层
3. 可定位：出问题时能说「这是链路层问题」，而不是含糊的「网络坏了」
```

「网络坏了」之所以难排查，本质是没有分层语言。有了层，每一层都有自己的观测工具 —— 1.5 节就会用到。

## 1.2 OSI 七层与 TCP/IP 四层

OSI 是国际标准化组织 1984 年提出的**参考模型**，TCP/IP 模型是互联网实际演进出来的**实现栈**。两者是「教学坐标系」与「真实地图」的关系。

```text
OSI 七层                    TCP/IP 四层        典型协议                数据单元
7 应用层        ┐                                                          
6 表示层        ├── 归入 ──────  应用层        HTTP DNS TLS SMTP SSH      报文
5 会话层        ┘                                                          
4 传输层        ──────── 对应 ── 传输层        TCP UDP SCTP               段 Segment
3 网络层        ──────── 对应 ── 网络层        IP ICMP                     分组 Packet
2 数据链路层    ┐
1 物理层        ┴─────── 合并 ── 网络接口层    以太网 WiFi PPP             帧 / 比特
```

对照表里有两处最容易记错：

```text
① OSI 的表示层/会话层在 TCP/IP 里没有独立层 —— 应用自己处理（TLS 管加密与会话恢复）
② TCP/IP 把链路层和物理层合并，因为这两层的实现差异太大，标准刻意不做规定
```

`curl` 在应用层，`ss` 在第四层，`ping` 在第三层，`arping` 在第二层 —— 这套词汇表足以让你把任何一句「网络有问题」翻译成可验证的命题。

## 1.3 封装与解封装：数据在层间的旅程

发送方自上而下加头，接收方自下而上脱头。每一层看到的都是「上一层给我的数据」，它并不知道也不关心里面装的是什么。

```text
发送端（应用 → 网卡）                          接收端（网卡 → 应用）

  "Hello"                                       HTTP/1.1 200 OK
    ↓ 加 TCP 头                                  ↑ 剥 TCP 头，交给应用
  [TCP头|Hello]                                  ↑ 剥 IP 头
    ↓ 加 IP 头                                    ↑ 剥以太网头
[以太网|IP|TCP|Hello]                            "Hello"
    ↓ 加以太网头+帧尾                            
[以太网头|IP|TCP|Hello|FCS]                      每一层只认自己的头长度
```

各层加的头开销（常用值）：

```text
以太网头 14 字节 + FCS 4 字节     TCP 头 20 字节（无选项）     IP 头 20 字节（无选项）
UDP 头只有 8 字节                 以太网最大帧 MTU 1500 字节 → 有效载荷约 1460
```

:::tip[MTU 与分片：一次性能感知的封装代价]
一个 TCP 段超过链路 MTU 就得 IP 分片，任何一片丢失都要重传整组，代价很高。现代网络靠 **MSS 协商**（TCP 建连时把 MSS 设为 MTU−40）让发送端根本不发超长段，而不是依赖分片。排查「小请求正常、大文件卡住」时，MTU 是第一个要怀疑的点，可用 `ping -M do -s 1472 对端IP` 逐段试探（Linux）。
:::

一个真实抓到的包长这样（`tcpdump -X` 的输出从链路层开始，这里只截取 IP 头起的 24 字节）：

```bash
$ sudo tcpdump -i eth0 -nn -X 'tcp port 80 and tcp[tcpflags] & tcp-syn != 0' -c 1
14:22:01.100001 IP 192.168.1.20.52760 > 110.242.68.66.80: Flags [S], seq 3932174412, win 64240
        0x0000:  4500 0028 0000 0000 4006 4058 c0a8 0114    ...(..@.8@...
        0x0010:  6ef2 4442 ce18 0050                        .n.DB..P
```

逐字段读一遍，层与层的边界一目了然：

```text
4500   IP 版本 4 + 头长 5（即 20 字节）+ 服务类型 00
0028   IP 总长 40 字节（SYN 没有净荷，正好 20 IP + 20 TCP）
4006   TTL = 0x40（64 跳）、协议号 = 0x06（TCP）—— 这个字节就是「交给上一层还是下一层」的路标
c0a8 0114  源 IP 192.168.1.20
6ef2 4442  目的 IP 110.242.68.66
ce18       源端口 52760        0050  目的端口 80（0x50）
```

**每一层的头都由上一层负责填好，自己只认自己的字段** —— 这就是为什么换网卡、换 WiFi、换 IP 都不会影响 HTTP 语义。

## 1.4 一次 HTTP 请求经过哪些层

以最简单的一条命令为例，看它如何被拆成各层的动作：

```bash
$ curl -v http://110.242.68.66/          # 直接对 IP 发请求，跳过 DNS 便于观察
* Connecting to 110.242.68.66:80
> GET / HTTP/1.1
> Host: 110.242.68.66
< HTTP/1.1 200 OK
```

这条命令在机器内部的旅程：

```text
1  应用层   curl 把 "GET / HTTP/1.1\r\nHost:...\r\n\r\n" 交给 socket 写接口
2  传输层   内核给字节流编号（序列号），加 TCP 头：源端口→80，SYN/ACK 标志
3  网络层   查路由表决定「从哪张网卡、下一跳给谁」，加 IP 头：源IP→目的IP
4  链路层   需要下一跳的 MAC 地址（未知就先发 ARP），加以太网头和 FCS
5  物理层   帧变成比特流上线
```

第 3、4 步是本章最关键的认知：**IP 决定「最终去哪」，MAC 决定「下一跳给谁」**。

```bash
$ ip route get 110.242.68.66      # 看内核怎么决策
110.242.68.66 via 192.168.1.1 dev eth0 src 192.168.1.20 uid 1000
    cache
```

`via 192.168.1.1` 就是默认网关 —— 数据包的 IP 头里目的地是公网 IP，但以太网帧的目的 MAC 却是网关的 MAC。这一点在 [第 2 章 · IP 与以太网](../02-ip-ethernet/) 展开。

## 1.5 抓包工具的视角：每层看到什么

抓包是分层的最好教具：同一个包在不同工具里呈现的层不同。

```bash
$ sudo tcpdump -i eth0 -nn 'tcp port 80' -c 3
14:22:01.100001 IP 192.168.1.20.52344 > 110.242.68.66.80: Flags [S], seq 1024, win 64240
14:22:01.104002 IP 110.242.68.66.80 > 192.168.1.20.52344: Flags [S.], seq 77, ack 1025
14:22:01.104200 IP 192.168.1.20.52344 > 110.242.68.66.80: Flags [.], ack 78
```

`tcpdump` 默认只解到第三、四层，所以看不到 HTTP 内容；要看完整字节得加 `-X` 或 `--immediate-mode` 配合 `wireshark` 的协议分层树。

```text
工具            主要工作层        能看到什么
tcpdump/wireshark  2~4 层        帧、IP、TCP 头 + 可选载荷
ss / netstat       4 层          本机 socket 状态、队列长度、收发窗口
ping                3 层          ICMP 往返，验证 IP 可达
arping              2 层          只出本机网段，验证 MAC 可达
curl               7 层          端到端语义，但看不清是哪层坏了
```

:::caution[抓包位置的盲区]
在容器或云主机里抓包，看到的是「已经过 NAT/网桥改写」的包。安全组、云厂商的虚拟交换机也可能丢包却不留痕迹。定位问题时要在**两端同时抓**：一端发出、一端收到，中间的差异才是网络的问题。
:::

## 1.6 常见误读：OSI 是标准，所以网络就是七层

这是初学者最根深蒂固的一个误解，也是本教程刻意把它单独列一节的原因。

```text
错误写法：
  「这个包在第三层被丢弃了，因为它没有通过表示层的校验」
  「TCP 是第四层协议，所以要经过四次转发」
  「交换机是二层设备，所以它在 OSI 第二层工作，路由器在第七层」

正确写法：
  「这个包被 iptables 的 INPUT 链丢了 —— 网络层之后、传输层之前」
  「TCP 是传输层协议，它是端到端的，中间路由器根本不看它」
  「二层交换机做 MAC 转发；三层交换机做 IP 路由；应用层是网关/代理的事」
```

理由有三条：

```text
1. OSI 从未被完整实现过。它是「讨论用的词汇表」，不是可部署的协议栈
2. 层数不等于跳数。四层是抽象职责，一包经过几个设备是拓扑问题
3. TCP/IP 栈的边界是模糊的：TLS 在会话层与表示层的位置，SCTP 也在传输层，
   QUIC 干脆把「传输+加密」塞进 UDP 之上（见 [第 5 章 · UDP 与 QUIC](../05-udp-quic/)）
```

:::danger[别用层号去推断设备能力]
「路由器就是三层设备」在今天已经站不住脚：家用路由器同时做 NAT（传输层端口改写）、DNS 代理（应用层）和防火墙。判断一台设备做了什么，永远看**它改写了哪一层的字段**，而不是它叫什么名字。
:::

## 本章小结

- 分层是为了把「端到端通信」的复杂度切成可替换、可分工、可定位的小块，这是所有网络排查的语言基础
- OSI 七层是教学坐标系，TCP/IP 四层是真实实现栈：应用/传输/网络/网络接口，会话与表示层由应用自己承担
- 发送自上而下逐层加头、接收自下而上逐层脱头；IP 决定最终目的地，MAC 决定这一跳交给谁
- 别把 OSI 当运行事实：判断设备做了什么要看它改写了哪层字段，抓包要在两端同抓才看得出丢包在哪一段
