**本章目标：**

- 判断什么场景该选 UDP，并说清「无连接」会带来哪些可观测的行为差异
- 理解 QUIC 选择 UDP 作为承载的真实原因（绕过内核而非绕过网络）
- 能说清 QUIC 的 0-RTT、连接迁移，以及丢包乱序到底由哪一层负责

## UDP 什么时候是对的选择

UDP 头只有 8 字节，没有握手、没有重传、没有拥塞控制、没有顺序保证。它的全部承诺是：**把一段数据报原封不动交给对端的某个端口，尽力而为**。

```text
UDP 头（8 字节）
 0        16       32
+---------+---------+---------+---------+
| 源端口  | 目的端口 |  长度    |  校验和  |
+---------+---------+---------+---------+
```

```text
该选 UDP 的四种情况
① 迟到比丢失更糟   实时音视频、游戏状态同步：过期的帧没有价值，重传只会加剧排队
② 一问一答就够     DNS、NTP、SNMP：一次请求一次响应，握手成本占比过高
③ 需要一对多       组播/广播：TCP 做不到「一次发、多方收」
④ 自己在用户态重造可靠性  QUIC、RTP+FEC、自研可靠协议：要逐流独立重传与优先级

该选 TCP 的情况（占绝大多数业务）
  文件、API、数据库：要求字节完整有序，不希望应用处理任何「缺了一段」的逻辑
```

:::tip[「UDP 更快」是个不准确的说法]
同一条链路上送同样的字节，UDP 省的是握手与头部，不是带宽。一旦网络拥塞，UDP 不会退让，反而会把邻居饿得更狠，自己也丢得更多。UDP 的优势是**延迟下限低且可控**，不是吞吐高。
:::

## 无连接带来的行为差异

「无连接」不是抽象说法，它会在四个具体行为上暴露出来。

```bash
# ① 没有 SYN，所以第一个包就直接带数据 —— 也就没有「连上了」这个事件
$ echo hi | nc -u -w1 10.0.0.9 8080     # 发完就走，对端不存在也不报错（nc 各实现选项不同，以 --help 为准）

# ② 对端没人监听 → 对端回 ICMP 端口不可达，本地上涨 UdpNoPorts 计数
$ nstat -az UdpInDatagrams UdpNoPorts UdpInErrors UdpRcvbufErrors
UdpInDatagrams     5
UdpNoPorts         3                       # 有人在往没监听的 UDP 端口发包
UdpRcvbufErrors    1                       # 接收缓冲区溢出，丢包发生在本机而非链路
```

```bash
# ③ 数据报边界保留：发 3 次 100 字节，对端 recv 三次各得 100 字节
#    TCP 则是把三段粘成 300 字节连续流，边界要应用自己划（HTTP 靠 Content-Length 就是为此）
# ④ 发送后是否报错，取决于 socket 有没有 connect 过
```

第 ④ 点最容易踩坑：

```text
错误写法：sendto() 到未 connect 的 UDP socket，然后指望代码能发现「对端不可达」
正确写法：内核只在**已 connect 的 UDP socket** 上把 ICMP 错误投递成 sendmsg 的
          ECONNREFUSED；未 connect 的 socket 会把它当 ICMP 噪声丢掉，写操作永远「成功」。
          想要错误反馈，就 connect() 之后再 send()。
```

:::caution[「UDP 也支持 connect」不是矛盾]
`connect()` 在 UDP 上不建连接、不发包，只是给内核记下「固定目的地址 + 只收来自这个地址的包」。好处有三：省掉每包的 `sendto` 参数、能收到 ICMP 错误、内核可做策略过滤。这也是 QUIC 用户态实现常用的写法。
:::

## 两个经典场景：DNS 与音视频

DNS 用 UDP 53，一个查询通常 40~120 字节，一次往返就完事：

```bash
$ dig +stats example.com | grep -E 'QUERY SIZE|SERVER|MSG SIZE'
;; Query time: 14 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
;; MSG SIZE  rcvd: 76

$ dig +tcp example.com          # 强制走 TCP 53：大响应或链路不可靠时的调试手段
```

DNS over UDP 的三条硬规则：

```text
1. 响应超过 512 字节会置 TC（截断）标志，客户端再用 TCP 重查一次
2. EDNS0 可以把上限提到 1232 甚至更大，但中间设备不一定放行 —— 见「DNS 放大攻击」的成因
3. 递归解析器有 5 秒左右的超时重发机制，所以偶发丢包只是变慢，不会变错
```

实时音视频（RTP / WebRTC）则反过来：**主动放弃重传**，靠三件事兜住质量：

```text
前向纠错 FEC     额外发冗余包，让接收方能自己还原 1~2 个丢失包
抖动缓冲区       接收端缓存 50~100ms 抹平乱序与网络抖动，直接换来等量延迟
关键帧请求       丢太多就要求发送方重发一个 I 帧（相当于「跳过中间态」而不是补中间包）
```

:::danger[别给实时流加应用层重传]
一旦加了，实时性立刻退化成「TCP 的行为 + UDP 的不可靠」。要抗弱网就加 FEC 和码率自适应（如 SVC 分层编码），这是视频团队的核心命题，不是网络层的。
:::

## QUIC 为什么建在 UDP 上

QUIC 不是「不靠谱的 UDP 之上随便加了点东西」，它是一个把传输层职责整体搬进用户态的完整协议（IETF 标准化为 RFC 9000 系列）。选 UDP 的理由是**部署**，不是性能本身。

```text
TCP + TLS 的 HTTP/2           QUIC / HTTP/3
────────────────────           ────────────────────
内核实现 TCP                    用户态实现传输 + TLS + 拥塞控制
中间设备会改写/误改 TCP 字段     中间设备基本只认 UDP，动不了载荷
协议改动 = 内核升级（按年计）    协议改动 = 应用发版（按周计）
```

真正的杀手级动机是这条：

```text
HTTP/2 over TCP 的头队阻塞（Head-of-Line Blocking）
  一条 TCP 上跑 5 个流，其中一个包丢了
  → TCP 必须把后面所有字节都扣在接收缓冲区，等重传补齐才交给应用
  → 即使另外 4 个流的数据完整，浏览器也拿不到
QUIC：每个流独立做丢包恢复，丢一个包只阻塞它所属的那一个流
```

:::tip[「绕过内核」的另一面是成本]
QUIC 在用户态意味着每次收发都要系统调用拷贝，因此高度依赖 `UDP_GRO`/`UDP_SEGMENT` 之类的内核卸载能力来摊薄成本。判断机器上 QUIC 表现时，`ss -u` 与 `nstat` 里的 UDP 队列溢出计数往往比 CPU 更早暴露问题。
:::

## 0-RTT 与连接迁移

QUIC 把「建连」和「加密握手」合并成一次往返，还可能省掉这一次：

```text
TLS 1.3 的 1-RTT
  ClientHello(带 SNI、密钥-share) ──▶
  ◀── ServerHello + Finished        之后再发 HTTP 请求 → 共 2 个 RTT

QUIC 的 1-RTT：握手与第一个数据请求在同一往返完成
QUIC 的 0-RTT：客户端用上次会话的密钥，在第一个包（Initial）里就带上早期数据
```

```bash
$ curl -s -o /dev/null -w 'proto=%{http_version} connect=%{time_connect}\n' --http3 https://127.0.0.1:8443/
$ ss -unp | head -5        # 看本机 UDP 端口的收发队列，QUIC 服务就是一个 UDP socket
```

`--http3` 需要 curl 编译时带上 HTTP/3 支持（`curl --version` 的 features 行能看到），否则用 `man curl` 确认后换用其它客户端测试。

0-RTT 的代价必须说清楚：**早期数据可被重放**。服务器在第一次连接还没完成地址验证（RETRY token）时就处理这些数据，攻击者可以把它复制多次送达，造成「非幂等操作被执行两次」。所以规范明确要求 0-RTT 只用于幂等请求（GET），写操作不允许。

连接迁移则是另一回事，靠 **连接 ID** 而不是四元组标识连接：

```text
TCP：连接 = 源IP:源端口 → 目的IP:目的端口，任一端换 IP 就必须重建（NAT 后换网络必断）
QUIC：连接 = Connection ID，换 WiFi→蜂窝时只需在新路径上验证归属（PATH_CHALLENGE），
      上层流状态与密钥全部保留 —— 移动端长会话、视频会议的掉线率因此显著下降
```

## 丢包与乱序由谁处理

这是理解 QUIC 的关键：**UDP 本身什么都不处理**，所以「谁处理」取决于上面盖了什么。

```text
裸 UDP           应用自己处理。没处理就是「丢了就丢了」，表现为画面花、指令丢失
RTP + RTCP       发送方靠 RTCP 反馈调码率；接收方靠抖动缓冲重排，丢包交给 FEC/关键帧
QUIC             协议栈自己实现一套可靠性：包号、ACK 帧、丢包检测、按流重传
自研可靠 UDP      常见于游戏：增量状态同步 + 快照补偿，丢包不重传而是「下次带最新的」
```

QUIC 的丢包判定与 TCP 不同，它给每个**包**（不是每个字节）分配单调递增的包号，重传的包用新包号，因此不会引入序号歧义；ACK 用区间（ACK Range）表达，等价于 TCP 的 SACK 但表达力更强。拥塞控制也在用户态，QUIC 默认实现是类 Cubic 的窗口算法（RFC 9002 给出参考模型），实现方可以按连接替换。

```bash
# 用 tcpdump 观察 QUIC 的不可解读性：载荷是密文的，连包号都看不到
$ sudo tcpdump -i any -nn 'udp port 443' -c 3
13:44:02.1 IP 10.0.0.5.39442 > 10.0.0.9.443: UDP, length 1200   ← 只能看到长度
```

:::caution[排障思路要跟着换]
TCP 时代「抓包看 seq/ack/retrans」的三板斧在 QUIC 上完全失效。可行做法是：应用侧导出连接级指标（RTT、每分钟丢包率、每流字节数），或临时关闭 HTTP/3 回退到 TCP 对比。这也是很多团队对全面上 QUIC 保持谨慎的实际原因——可观测性要重建。
:::

## 综合练习：三个需求各选哪种传输

```text
需求 A：内网服务间调用，单次请求 2KB，P99 延迟要求 5ms 以内，链路 RTT 0.3ms
需求 B：移动端 App 的实时弹幕消息，允许偶发丢，要求切换网络不重连
需求 C：文件同步服务，弱网（丢包 5%）下吞吐要稳定
```

```text
参考答案与理由：
A  TCP（或 Unix socket / 共享内存）。RTT 0.3ms 时握手只 0.3ms，长连接 + 连接池下几乎免费；
   换成 UDP 要自己实现可靠性，而收益只是省 8 字节头 —— 不划算，且 P99 抖动反而更难控。
B  QUIC / HTTP/3（或 WebSocket over TCP + 应用层重连）。换网络不重连正是连接迁移的用武之地；
   弹幕可丢，也可考虑裸 UDP + 应用层序号做去重与丢弃过期。
C  QUIC。弱网下 TCP 的丢包重传会退化为 RTO 惩罚（见 [第 4 章 · 可靠传输与拥塞控制](../04-tcp-reliability/)），
   而 QUIC 的按流恢复 + 用户态拥塞控制能更快从丢包里恢复；若必须兼容旧客户端，就保留 TCP 并启用 BBR。
```

## 本章小结

- UDP 的价值是低延迟下限与一对多能力，代价是把可靠性、顺序、拥塞全部推给应用；选它要有明确理由
- 「无连接」的四个可见后果：无 SYN、错误只在 connect 过的 socket 上暴露、保留数据报边界、靠 ICMP 计数排障
- QUIC 建在 UDP 上是为了绕开内核与中间设备的部署锁死，核心收益是消除跨流头队阻塞、支持连接迁移
- 丢包乱序永远由「UDP 之上那一层」负责；QUIC 用包号 + ACK 帧 + 用户态拥塞控制自管，代价是可观测性要重建
